# PEKEFE ENGINEERING HANDBOOK v1.0 - SUPREME TECHNICAL DIRECTIVE

All technical architecture, code generation, refactoring, performance optimization, and engineering decisions MUST strictly comply with `docs/engineering/PEKEFE_ENGINEERING_HANDBOOK_v1.0.md`.

## NON-NEGOTIABLE ENGINEERING PRINCIPLES (Chapter 01):
1. **10-Year Software Mindset:** Write code for the next ten years. Never optimize for short-term speed at the expense of long-term quality.
2. **Core Priorities:** Maintainability, Scalability, Readability, Performance, Reliability, Security, Extensibility, Developer Experience.
3. **Pillars:**
   - Readable code over clever code.
   - Explicit over implicit.
   - Composition over inheritance.
   - Server Components over Client Components.
   - Static rendering over dynamic rendering.
   - Performance over visual effects.
   - Accessibility over aesthetics.
   - Consistency over personal preference.
4. **Strictly Forbidden:**
   - Business logic duplication & hardcoded values.
   - Ignoring TypeScript errors, disabling ESLint/a11y warnings.
   - Committing commented-out code or `console.log`.
   - Shipping experimental code to production.
   - Ignoring Lighthouse scores, SEO best practices, or Core Web Vitals.
## PROJECT STRUCTURE & FEATURE ARCHITECTURE (Chapter 03):
1. **Folders as Documentation:** Structure must communicate domain architecture (`src/app`, `src/features`, `src/components`, `src/shared`, `src/services`, `src/actions`, `src/schemas`, `src/types`).
2. **Feature Module Standard:** `src/features/[feature-name]/` with `components`, `actions`, `hooks`, `schemas`, `types`, `services`, `utils`, `tests`, `README.md`.
3. **Module Limit:** No feature module may exceed 5,000 lines of code without being refactored/split into sub-modules.
## TYPESCRIPT & VALIDATION STANDARDS (Chapter 04):
1. **Strict Mode Mandatory:** Zero `any`, no implicit `any`, no unsafe type casting (`as unknown as T`), no `@ts-ignore`.
2. **Type Declarations:** `interface` for object contracts/API types; `type` for unions, primitives, and function signatures. Use `readonly` whenever possible.
3. **Enum Prohibition:** Avoid TS `enum`s; use `const` assertions (`as const`) and string literal union types instead.
4. **Zod Validation Mandate:** Never trust client/external data. Every Server Action, API endpoint, form input, and URL param MUST be validated using **Zod** schemas.
## NEXT.JS ARCHITECTURE STANDARDS (Chapter 05):
1. **App Router Standard:** Built on Next.js App Router paradigm.
2. **Server Components First Rule:** Every new page or component MUST first be attempted as a Server Component.
3. **Server Actions & Streaming:** Use Server Actions for all mutations/data fetching; use `<Suspense>` boundaries and streaming for progressive hydration.
4. **Strict Client Component Rules ('use client'):** Only use `'use client'` for: (1) Browser APIs, (2) Client animations, (3) Interactive state (`useState`), (4) Direct UI event handlers (`onClick`). *Nothing else justifies `'use client'`.*
## REACT COMPONENT STANDARDS (Chapter 06):
1. **Rendering Library Philosophy:** React is a rendering library, not a database or global state cache.
2. **Component Rules:** Pure, small, reusable, single responsibility. Render functions must have ZERO side effects.
3. **Measured Optimization:** Use `useMemo` and `useCallback` ONLY when measured profiling proves a re-render bottleneck. No premature optimization clutter.
4. **Context Restriction:** Use React Context only for global UI state (theme, modals, toasts).
5. **Component Size Limits:** Target 200 lines; **maximum hard limit 400 lines**. Any component exceeding 400 lines MUST be refactored/split immediately.
## TAILWIND & DESIGN SYSTEM IMPLEMENTATION (Chapter 07):
1. **Design Tokens Mandatory:** Tailwind is our implementation layer, NOT our design system. All styles must use design tokens (`bg-burgundy-500`, `bg-cream-100`, `text-slate-900`, `text-gold-400`).
2. **Forbidden Styles:** Zero arbitrary colors (e.g. `bg-[#800020]`), zero arbitrary pixel spacing (e.g. `p-[13px]`), zero React `style={{ ... }}` inline objects.
3. **Theme Centralization:** All colors, spacing, radius, typography, shadows, and animations must originate from `tailwind.config.ts` or design token definitions.
## CODE QUALITY & CODE REVIEW STANDARDS (Chapter 08):
1. **The 9 PR Quality Dimensions:** All merges MUST satisfy (1) TypeScript (0 errors), (2) ESLint (0 warnings), (3) Formatting, (4) Accessibility (a11y), (5) Performance (60 FPS, Core Web Vitals), (6) Security (Zod schemas), (7) SEO, (8) Tests, (9) Documentation.
2. **The 6 Code Review Questions:** Validate before merging: *Simpler? Reusable? Testable? Documented? Scalable? Understandable in 15 mins?*
## FEATURE DOCUMENTATION STANDARDS (Chapter 09):
1. **Mandatory Documentation:** Every feature module (`src/features/[feature-name]/`) MUST contain a `README.md`.
2. **7 Required Sections:** (1) Overview & Purpose, (2) Architecture & Component Tree, (3) Data Flow & User Journey, (4) Dependencies, (5) Future Improvements, (6) Known Limitations, (7) Usage Examples.
## ENGINEERING CONSTITUTION & DECADE RESPONSIBILITY (Chapter 10):
1. **Supreme Technical Authority:** No engineer, AI assistant, agency, or contributor may intentionally violate Volume 01 standards.
2. **Quality Dimension Alignment:** Every architectural decision MUST improve Maintainability, Scalability, Performance, Security, Readability, Developer Experience, Accessibility.
3. **Redesign Directive:** If a requested implementation conflicts with Volume 01, it MUST be redesigned.
4. **Zero Compromise Rule:** Never lower engineering quality to complete a task faster.
5. **The 10-Year Mandate:** The PEKEFE platform is expected to evolve for the next decade. Every line of code must respect that responsibility.

# PEKEFE ARCHITECTURE HANDBOOK v1.0 - SUPREME ARCHITECTURAL DIRECTIVE

All software architecture, domain boundary definitions, data flow pipelines, state management, service taxonomies, and event architectures MUST strictly comply with `docs/architecture/PEKEFE_ARCHITECTURE_HANDBOOK_v1.0.md`.

## NON-NEGOTIABLE ARCHITECTURAL PRINCIPLES (Volume 02):
1. **The Golden Rule (Chapter 01):** Business Rules must NEVER depend on Frameworks. Frameworks may change; business rules must survive.
2. **Domain Ownership & Isolation (Chapter 02):** Core domains (Commerce, Catalog, Recipes, ERP, Content, Media, Search, AI, B2B) own their rules, schemas, services, tests, and docs. No domain may directly manipulate another domain's internal state.
3. **Feature First Structure (Chapter 03):** Self-contained `src/features/[feature-name]/` layout (`components`, `actions`, `services`, `schemas`, `types`, `hooks`, `tests`, `README.md`). Inter-feature communication strictly via public interfaces or events.
4. **Server First Mandate (Chapter 04):** DB access, auth, permissions, and business logic exist ONLY on the server. Client Components allowed ONLY for interaction, form inputs, animation, maps, charts, media players, or local UI state.
5. **Strict State Hierarchy (Chapter 05):** `Server State` $\rightarrow$ `URL State` $\rightarrow$ `Form State` $\rightarrow$ `Local State` $\rightarrow$ `Context` $\rightarrow$ `External Store`. Never store duplicated data; zero giant contexts.
6. **Mandatory Single Data Flow Path (Chapter 06):**
   - **Request:** `Browser` $\rightarrow$ `Server Action` $\rightarrow$ `Application Service` $\rightarrow$ `Domain Service` $\rightarrow$ `Repository` $\rightarrow$ `Database`.
   - **Response:** `Database` $\rightarrow$ `Repository` $\rightarrow$ `Domain Service` $\rightarrow$ `Application Service` $\rightarrow$ `Server Component` $\rightarrow$ `Browser`.
   - *No shortcuts allowed! Direct DB calls from components or direct repository calls from Server Actions are strictly forbidden.*
7. **Dependency Direction (Chapter 07):** Allowed: `UI` $\rightarrow$ `Application` $\rightarrow$ `Domain` $\rightarrow$ `Infrastructure`. Forbidden: `Infrastructure` $\rightarrow$ `UI`, `Repository` $\rightarrow$ `Component`, `Database` $\rightarrow$ `Component`.
8. **Repository Rule (Chapter 08):** Repositories ONLY execute CRUD operations (Read, Write, Update, Delete). Zero business rules in Repositories; decisions belong to Domain Services.
9. **Service Layer Taxonomy (Chapter 09):**
   - **Application Service:** Workflow coordination & transaction boundaries.
   - **Domain Service:** Core business rules & entity logic.
   - **Infrastructure Service:** External 3rd party integrations (payments, shipping, email).
10. **Validation & Security (Chapters 10 & 11):** Mandatory Zod schema validation before business logic execution. Authentication (identity) and Authorization (permissions/roles) are completely independent.
11. **Platform Capabilities & Decoupling (Chapters 12 – 18):**
    - Media abstracted through Media Services (zero hardcoded file paths).
    - Event Architecture (`OrderCreated`, `StockUpdated`, `RecipePublished`) for decoupled domain sync.
    - Automated SEO (Metadata, JSON-LD Schema.org, Sitemap).
    - Search & AI as platform-wide services.
    - ERP as a Core Domain communicating via events.
12. **Observability (Chapter 19):** Errors, performance, DB queries, payments, search, and Server Actions MUST be measurable.

# PEKEFE DESIGN SYSTEM BIBLE v1.0 - SUPREME DESIGN DIRECTIVE

All user interfaces, design tokens, layout grids, components, micro-interactions, form behaviors, typography scales, and visual presentations MUST strictly comply with `docs/design-system/PEKEFE_DESIGN_SYSTEM_BIBLE_v1.0.md`.

## NON-NEGOTIABLE DESIGN SYSTEM RULES (Volume 03):
1. **Design Philosophy (Chapter 01):** PEKEFE is curated. The interface disappears; food, story, and craftsmanship remain. Calm, Elegant, Editorial, Natural, Timeless, Premium, Readable, Minimal, Human. *Never corporate, template, marketplace, startup, AI-generated, or overdesigned.*
2. **Design Tokens Mandatory (Chapter 02):** Every UI value originates from tokens (Colors, Typography, Spacing, Radius, Shadow, Border, Motion, Container, Grid, Breakpoints). Zero hardcoded values.
3. **Spacing System (Chapter 03):** Spacing creates luxury. Base unit: `8px`. Scale: `4, 8, 12, 16, 24, 32, 40, 48, 64, 80, 96, 120, 160, 240px`. Never invent ad-hoc spacing.
4. **Grid Alignment (Chapter 04):** Desktop: 12 Cols, 1280px Container, 24px Gutter, 64px Margin, 120px Section Gap. Tablet: 8 Cols. Mobile: 4 Cols, 20px Margin, 64px Section Gap.
5. **Typography Scale (Chapter 05):** Display XXL (96px) to Caption (12px). Max line width: 75 chars. Min body size: 16px.
6. **Color System 70/20/8/2 Rule (Chapter 06):** 70% Neutral (Cream/Linen), 20% Primary (Burgundy), 8% Typography (Dark Slate, *no `#000000`*), 2% Accent Gold (*Gold is earned*).
7. **Surfaces & Elevation (Chapter 07):** Surface 0 (Background) $\rightarrow$ Surface 1 (Cards) $\rightarrow$ Surface 2 (Elevated) $\rightarrow$ Surface 3 (Modal). Soft, subtle shifts only.
8. **Button Hierarchy (Chapter 08):** Primary (Max 1 per section), Secondary, Ghost, Text, Danger. Must support Loading, Disabled, Success states.
9. **Anxiety-Reducing Forms (Chapter 09):** Label, Helper, Validation, Focus, Success, Error, Disabled, Autocomplete on all form fields.
10. **Quiet Card Containers (Chapter 10):** Max 1 elevation, max 1 border, max 1 shadow per container. Never stack decorative effects.
11. **Unified Table Component (Chapter 11):** ERP, CMS, Inventory, and Finance share ONE table component (Sorting, Filtering, Search, Pagination, Bulk Select, Keyboard Nav).
12. **Modals & Drawers (Chapters 12 & 13):** Modals max width 960px (Escape/Focus trapped). Drawers for filters, cart, notifications, quick edit (*never large workflows*).
13. **Disappearing Navigation (Chapter 14):** Max 7 primary nav items. Sticky header shrinks on scroll.
14. **Unified Icon System (Chapter 15):** 1 outline icon family only, consistent stroke, optical alignment. Zero colorful/mixed icons.
15. **Explanatory Motion (Chapter 16):** Durations: 120ms, 180ms, 240ms, 320ms, 480ms. Natural easing, GPU-accelerated. *Zero bounce, zero elastic wobble.*
16. **Responsive Adaptation (Chapter 17):** Desktop-First Architecture, Mobile-First Implementation. No hidden desktop features; reorganized, not shrunk.
17. **Accessibility Mandate (Chapter 18):** WCAG 2.1 AA minimum (AAA preferred). Keyboard navigation, ARIA labels, visible focus rings, high contrast.

1. **Emotional Usability Mandate:** People do not buy food; people buy *Trust, Tradition, Health, Family, Memories, Pride, Hospitality, Authenticity*. The interface must strengthen these emotions, never interrupt them.
2. **Primary UX Goals:** (1) Reduce Cognitive Load, (2) Increase Trust, (3) Increase Product Understanding, (4) Reduce Purchase Anxiety, (5) Increase Premium Perception, (6) Increase Repeat Purchases, (7) Increase Emotional Connection.
## CUSTOMER PSYCHOLOGY & TRUST CHAIN (Chapter 02):
1. **Uncertainty to Confidence Transformation:** Customers arrive with uncertainty. The platform must transform uncertainty into confidence.
2. **Immutable Psychological Transformation Chain:**
   $$\text{Education} \longrightarrow \text{Transparency} \longrightarrow \text{Proof} \longrightarrow \text{Story} \longrightarrow \text{Trust} \longrightarrow \text{Purchase}$$
## COGNITIVE LOAD & SIMPLICITY (Chapter 03):
1. **The Triple Reduction Rule:** (1) Reduce Choices (curated options over overwhelming catalogs), (2) Reduce Distractions (remove popups & competing CTAs), (3) Reduce Decisions (guide smoothly to the next logical step).
## VISUAL HIERARCHY & FOCUS (Chapter 04):
1. **Single Objective Mandate:** Every screen MUST have exactly one primary objective. Every secondary element exists solely to support that objective.

# PEKEFE COMMERCE BIBLE v1.0 - SUPREME COMMERCIAL DIRECTIVE

All e-commerce features, catalog architecture, pricing models, checkout flows, promotion engines, B2B portals, and revenue strategies MUST strictly comply with `docs/commerce/PEKEFE_COMMERCE_BIBLE_v1.0.md`.

## NON-NEGOTIABLE COMMERCE RULES (Volume 05):
1. **Commerce Philosophy (Chapter 01):** PEKEFE operates like a premium gastronomy house, not a discount marketplace. Maximize customer LTV and trust. Protect: Quality, Trust, Profitability, Brand Perception, Operational Sustainability, Long-Term Loyalty.
2. **Dual Business Model (Chapter 02):** B2C (Storytelling & Experience) and B2B (Pricing tiers, credit, logistics) share the same product catalog but remain technically separated.
3. **Catalog & Data Standard (Chapters 03 & 04):** 8 Primary Categories + 7 Curated Collections (each with SEO landing pages). Mandatory full data fields (Origin, Village, Producer, Ingredients, Allergens, Storage, Culinary Pairings, HD Media, JSON-LD Schema). Incomplete products cannot be published.
4. **Value-Based Clean Pricing (Chapter 05):** Value-based pricing reflecting artisan effort & quality. **RULES:** ZERO `.99` psychological prices (use clean prices: `₺420`, `₺850`, `₺1.250`). Never engage in supermarket price wars.
5. **Discount Policy (Chapter 06):** Discounts are exceptional. Allowed: Seasonal, limited harvest pre-orders, gift bundles, B2B tiers. FORBIDDEN: Fake discounts, countdown timers, inflated reference price cross-outs, fake inventory urgency.
6. **B2B Tiers & MOQ (Chapters 07 & 08):** Bronze, Silver, Gold, Platinum tiers (Wholesale pricing never visible to retail). Per-product MOQ supported.
7. **Cart & Cross-Sell (Chapters 09 & 10):** Decision-support cart with zero hidden fees. Cross-sell max 3 authentic culinary pairings (e.g. Dut Pekmezi $\rightarrow$ Tahin).
8. **Checkout, Payments & Shipping (Chapters 11 - 13):** Cart $\rightarrow$ Address $\rightarrow$ Delivery $\rightarrow$ Payment $\rightarrow$ Review $\rightarrow$ Confirmation. Autocomplete, guest checkout, SSL badges. Transparent installments. Cold-chain logistics tracking.
9. **Order Model & Returns (Chapters 14 & 15):** Event-driven order status logging. Trust-first returns with clear food safety rules.
10. **Loyalty & Gift Commerce (Chapters 16 & 17):** Prestigious loyalty (Harvest early access, VIP events). Gifting stream (Gift notes, multi-address, price-free receipts).
11. **Commerce Constitution (Chapter 20):** **Revenue is important. Brand reputation is more important.** If a feature increases short-term conversion but damages premium brand perception, **the feature MUST be rejected**.
